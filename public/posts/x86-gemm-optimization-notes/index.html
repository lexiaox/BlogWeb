这个项目在研究什么#

我这次关注的是一个高性能计算里非常经典的问题：
单精度矩阵乘法（GEMM）在 x86_64 架构下，怎样一步步从朴素实现优化到高性能实现。

这个问题有代表性，因为 GEMM 不只是一个算法题，它几乎把这些主题全串起来了：

  • 存储层次结构
  • cache 局部性
  • 指令级并行
  • SIMD 向量化
  • 寄存器分块

换句话说，这不是单纯“把代码改快一点”，而是在理解硬件之后，让算法更贴近硬件。

为什么朴素 GEMM 会慢#

朴素矩阵乘法通常会写成三层循环。
问题不在于它“不会算”，而在于它的访存方式对 cache 很不友好。

尤其是在行主序存储下，如果按常见的 i-j-k 顺序写，矩阵 B 的访问会出现大跨度跳跃：

  • 空间局部性差
  • CPU 预取不容易生效
  • cache miss 和 TLB miss 都会增加

所以很多时候，程序慢并不是算力不够，而是内存访问模式已经把性能卡死了。

我的优化路径#

这次我按三层思路推进：

  1. 先改访问模式
  2. 再改缓存复用
  3. 最后改指令级并行

1. 循环重排#

我先把循环顺序从常见的 i-j-k 调整到更适合行主序访问的顺序。
这么做的目标很明确：

  • 让对 B 和 C 的访问更连续
  • 提升空间局部性

这是最先见效的一步，因为它直接改善了数据访问模式。

2. 缓存分块#

仅靠循环重排还不够。
矩阵规模一大，工作集超出 L1/L2 cache 后，性能还是会掉下来。

所以第二步我引入了 blocking / tiling：

  • 把大矩阵切成子块
  • 让参与计算的子块尽量驻留在 cache 中
  • 尽可能重复利用已经加载的数据

这一层本质上是在提高时间局部性。

3. AVX2 + 寄存器分块#

最后才是 SIMD。
很多人会觉得“优化 = 上 AVX2”，但如果前两步没做好，单纯替换成向量指令，收益通常不会理想。

我最后结合了：

  • AVX2 256 位向量寄存器
  • FMA
  • 寄存器分块

思路是让多个累加寄存器并行工作，减少强依赖链带来的流水线停顿。

实验结果#

我整理后的核心结果如下：

优化策略 核心思路 性能 (GFLOPS) 相对朴素实现加速比
朴素实现 基准版本 0.73 1.0x
循环重排 优化空间局部性 24.55 33.6x
缓存分块 优化时间局部性 27.68 37.9x
AVX2 + 寄存器分块 指令级并行优化 33.10 45.3x

这个结果里最值得注意的一点是：

循环重排带来的收益已经非常夸张。
这说明在这类问题里，先把访存方式改对，比一上来谈 SIMD 更关键。

这次实验让我真正理解了什么#

1. 性能优化首先是访存优化#

很多时候，瓶颈根本不是浮点运算本身，而是数据怎么进入 CPU。

如果访存模式不对：

  • cache 利用率低
  • 内存带宽浪费
  • 硬件预取失效

那后面的 AVX2 也发挥不出来。

2. blocking 是非常“硬核”的工程技巧#

以前我知道分块是常见优化，但这次实验让我真正理解它不是一个“理论名词”，而是决定性能上限的核心手段之一。

它本质上是在问：

  • 怎样安排计算顺序，才能让已经进 cache 的数据多用几次

3. SIMD 不只是“并行算 8 个数”#

真正难的部分不只是写 intrinsics，而是理解：

  • 指令依赖
  • 寄存器使用
  • 延迟掩盖
  • 微内核展开

也就是说，SIMD 优化不只是语法问题，而是调度问题。

这类项目为什么值得写进博客#

因为它很能代表我的技术兴趣。

它不是一个“能立刻看到漂亮界面”的项目，但它反映了我在关注这些更底层的问题：

  • 程序为什么慢
  • 硬件到底在帮我做什么
  • 软件怎么更贴近硬件

这类项目记录下来，不只是为了总结一次实验，更像是在记录我自己的思考方式。

后面还想继续做什么#

如果继续往下做，我最想补的是：

  • 更系统地测不同 block size 对性能的影响
  • 把 AVX2 微内核实现单独拆出来分析
  • 对比 OpenBLAS / MKL 的实现思路
  • 继续往多线程和 NUMA 场景扩展

这类问题往下挖，会越来越接近真正的高性能计算优化方法论。
